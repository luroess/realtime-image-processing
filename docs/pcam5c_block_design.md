## 1. High-level functional architecture

Primary AXI4-Stream links in BD:

- `MIPI_CSI_2_RX_0/m_axis_video -> AXI_BayerToRGB_0/AXI_Slave_Interface`
- `AXI_BayerToRGB_0/AXI_Stream_Master -> AXI_GammaCorrection_1/s_axis_video`
- `AXI_GammaCorrection_1/m_axis_video -> axi_vdma_0/S_AXIS_S2MM`
- `axi_vdma_0/M_AXIS_MM2S -> v_axi4s_vid_out_0/video_in`

## 2. AXI bus usage in this design

### 2.1 AXI4-Stream video path

The pixel pipeline follows AXI4-Stream video semantics end-to-end, then converts to native video only at the output boundary (`v_axi4s_vid_out_0`).

- Ingress stream originates at `MIPI_CSI_2_RX_0/m_axis_video`
- Custom processing in `AXI_BayerToRGB_0` and `AXI_GammaCorrection_1`
- Frame buffering through `axi_vdma_0` (S2MM write / MM2S read)
- Egress stream into `v_axi4s_vid_out_0/video_in`

Protocol constraints for this project are aligned with UG934 Chapter 2:

- `TUSER[0]` is SOF
- `TLAST` is EOL
- Only active video pixels are carried in AXI4-Stream
- Periodic sync data must not be encoded in `TUSER` or pixel payload

### 2.2 AXI4-Lite control path

The PS7 `M_AXI_GP0` master drives control/configuration for all programmable video IP through `ps7_0_axi_periph`.

Control address map:

| IP | AXI4-Lite slave | Base address | Range |
|---|---|---:|---:|
| `axi_vdma_0` | `S_AXI_LITE/Reg` | `0x43000000` | `64K` |
| `vtg` | `ctrl/Reg` | `0x43C00000` | `64K` |
| `AXI_GammaCorrection_1` | `s_axil/reg0` | `0x43C10000` | `64K` |
| `MIPI_CSI_2_RX_0` | `S_AXI_LITE_reg` | `0x43C20000` | `64K` |
| `MIPI_D_PHY_RX_0` | `S_AXI_LITE_reg` | `0x43C30000` | `64K` |
| `video_dynclk` | `s_axi_lite/Reg` | `0x43C40000` | `64K` |

### 2.3 AXI4 memory-mapped data path (VDMA <-> DDR)

VDMA configuration highlights:

- MM2S enabled, S2MM enabled
- Stream widths: 24-bit on both MM2S and S2MM sides
- Memory widths: 64-bit on both AXI-MM channels
- 3 frame stores
- Dynamic resolution enabled
- Scatter-gather disabled

## 3. Timing model and UG934 Chapter 2 relevance

UG934 Chapter 2 key points relevant here:

- AXI4-Stream video carries active pixels + SOF/EOL only
- Timing is propagated/configured through AXI4-Lite and dedicated timing IP
- VTC provides timing detector + timing generator capability
- Using `TUSER` for periodic sync transport is prohibited

How this BD implements that model:

- `vtg` (`xilinx.com:ip:v_tc:6.2`) is configured with:
  - `VIDEO_MODE = 720p`
  - `enable_generation = true`
  - `enable_detection = false`
- `vtg/vtiming_out` drives `v_axi4s_vid_out_0/vtiming_in`
- `v_axi4s_vid_out_0` converts AXI4-Stream video to native video using external timing
- `axi_vdma_0` implements both frame-buffer legs around external memory (`S2MM` ingress + `MM2S` egress)

Interpretation:

- This design is a timing-generator-driven output path.
- It does not use a separate VTC timing detector stage in the current BD.
- Ingress camera data already arrives as AXI4-Stream from the CSI-2 receiver.
- The BD matches the UG934 frame-buffer pattern: stream processing is decoupled from output timing by AXI VDMA + DDR.

## 4. Clock and reset domains

Domain summary:

- `s_axil_clk_50`: AXI4-Lite/control path
- `mm_clk_150`: stream processing + VDMA + HP memory interfaces
- Pixel domain (`PixelClk_Generator_clk_out1`): VTC + AXI4S-to-Video-Out native side + RGB2DVI

## 7. Detailed functionality of each IP core

### 7.1 [`processing_system7_0`](../vivado/Zybo-Z7-10-Pcam-5C-hw.xpr/hw/hw.gen/sources_1/bd/system/synth/system.vhd#L3463) (Zynq PS7)

- Functional role: system orchestrator, DDR memory controller, and AXI control master.
- Main interfaces: `M_AXI_GP0` (AXI4-Lite control master), `S_AXI_HP0` and `S_AXI_HP2` (high-performance AXI slave ports for VDMA), `DDR`, `FIXED_IO`, `GPIO_0`, `IIC_0`, `IRQ_F2P`.
- What it does in this design: software on ARM configures camera path, VDMA, timing generator, dynamic clocking, and gamma tables over AXI-Lite.
- Why it is necessary: without PS software, most video IP remains unconfigured and frame movement/timing generation are not started.
- Domain behavior: emits `FCLK_CLK0` and `FCLK_RESET0_N`, which seed all PL clock/reset domains through `clk_wiz_0` and reset controllers.

### 7.2 `MIPI_D_PHY_RX_0`

- Functional role: physical/electrical receiver for MIPI CSI-2 lane signaling (LP + HS).
- Main interfaces: external lane pins (`dphy_hs_clock`, `dphy_clk_lp_*`, `dphy_data_hs_*`, `dphy_data_lp_*`), `D_PHY_PPI` (to CSI-2 RX), `S_AXI_LITE` (control/status).
- Configuration highlights: 2 data lanes, AXI-Lite enabled, LP-from-lane0 disabled, debug disabled.
- What it does in this design: converts wire-level MIPI transitions into byte/packet-level PPI signals and provides `RxByteClkHS` to `MIPI_CSI_2_RX_0`.
- Domain behavior: requires dedicated reference clock (`ref_clk_200`) and dedicated async reset path (`aRst`).

### 7.3 `MIPI_CSI_2_RX_0`

- Functional role: CSI-2 protocol decode and packet-to-video conversion.
- Main interfaces: `rx_mipi_ppi` (from D-PHY), `m_axis_video` (to Bayer IP), `S_AXI_LITE` (control/status).
- Configuration highlights: `kTargetDT=RAW10`, `kLaneCount=2`, AXI stream width 40 bits, max 4 samples/clock.
- What it does in this design: strips CSI-2 framing and emits AXI4-Stream video with `TDATA/TVALID/TREADY/TUSER/TLAST`.
- Framing behavior: source of SOF/EOL markers for downstream custom video processing.

### 7.4 `AXI_BayerToRGB_0`

- Functional role: debayer conversion from RAW10 Bayer-pattern pixels to packed RGB-style stream.
- Main interfaces: `AXI_Slave_Interface` (input stream), `AXI_Stream_Master` (output stream), `StreamClk`, `sStreamReset_n`.
- Configuration highlights: input width 40, output width 32, max samples/clock 4.
- What it does in this design: reconstructs color channels from Bayer samples (line-buffer based interpolation pipeline) and forwards stream framing/flow control.
- Integration implication: this is the first custom compute stage; its output format is the expected input for `AXI_GammaCorrection_1`.

### 7.5 `AXI_GammaCorrection_1`

- Functional role: per-channel intensity remapping (gamma correction) using programmable coefficient tables.
- Main interfaces: `s_axis_video` (32-bit input stream), `m_axis_video` (24-bit output stream), `s_axil` (AXI-Lite registers), `StreamClk`, `AxiLiteClk`.
- Configuration highlights: input width 32, output width 24, input color width 10 bits.
- What it does in this design: remaps incoming component values and compresses to 24-bit output stream consumed by VDMA S2MM.
- Control behavior: coefficients and mode are software-controlled via AXI-Lite; stream and control domains have independent clocks/resets.

### 7.6 `axi_vdma_0` (AXI Video DMA)

- Functional role: bidirectional bridge between AXI4-Stream video and DDR frame memory.
- Why it exists: decouples processing throughput/clocking from output timing requirements, enabling stable HDMI timing even when upstream timing and downstream timing differ.
- UG934 mapping: this is exactly the "Video to Frame Buffer" and "Video from Frame Buffer" pair shown in Figure 2-3.

Channel-level purpose:

| Channel | UG934 naming | Direction | Role in this design |
|---|---|---|---|
| `S2MM` | Video to Frame Buffer | AXI4-Stream -> DDR | Captures processed camera frames (`AXI_GammaCorrection_1`) into memory |
| `MM2S` | Video from Frame Buffer | DDR -> AXI4-Stream | Replays stored frames into output pipeline (`v_axi4s_vid_out_0`) |

#### Video to Frame Buffer (`S2MM`) behavior

1. Consumes incoming AXI4-Stream (`S_AXIS_S2MM`) from `AXI_GammaCorrection_1/m_axis_video`.
2. Uses SOF/EOL stream framing (`TUSER[0]` / `TLAST`) together with programmed dimensions to delimit frame lines in memory.
3. Writes bursts through `M_AXI_S2MM` into DDR (via `axi_mem_intercon_1` -> PS `S_AXI_HP2`).
4. Advances frame-store pointer and signals completion/events through `s2mm_introut`.

#### Video from Frame Buffer (`MM2S`) behavior

1. Reads frame lines from DDR through `M_AXI_MM2S` (via `axi_mem_intercon` -> PS `S_AXI_HP0`).
2. Reconstructs AXI4-Stream on `M_AXIS_MM2S` and forwards to `v_axi4s_vid_out_0/video_in`.
3. Supports frame read scheduling/sync modes so readout can align with output timing policy.
4. Signals channel events through `mm2s_introut`.

#### Ports shown in the IP block view

| Port group | Purpose |
|---|---|
| `S_AXI_LITE` | Control/status registers (base `0x43000000`) |
| `S_AXIS_S2MM` | Stream input for write channel (Video to Frame Buffer) |
| `M_AXIS_MM2S` | Stream output for read channel (Video from Frame Buffer) |
| `M_AXI_S2MM` | AXI-MM master writes to DDR |
| `M_AXI_MM2S` | AXI-MM master reads from DDR |
| `s_axi_lite_aclk`, `m_axi_*_aclk`, `m_axis_mm2s_aclk`, `s_axis_s2mm_aclk` | Separate clocks for control/read/write/stream sides |
| `axi_resetn` | Active-low core reset |
| `mm2s_frame_ptr_out`, `s2mm_frame_ptr_out` | Current frame-store pointer visibility |
| `mm2s_introut`, `s2mm_introut` | Interrupt outputs to PS (through `xlconcat_0`) |

#### Current configuration in this project

- Channel enable: MM2S enabled and S2MM enabled.
- Stream widths: `24` bits on both channels.
- Memory widths: `64` bits on both MM2S/S2MM AXI-MM interfaces.
- Frame stores: `3`.
- Dynamic resolution: enabled.
- Scatter-gather: disabled (direct register programming mode).
- Fsync features: enabled with channel-specific source modes configured; flush-on-fsync enabled.

#### How this ties to `vtg` and UG934 Figure 2-3

- `vtg` defines output timing cadence for display generation.
- VDMA MM2S supplies pixels from memory at a rate coordinated with output timing/consumer backpressure.
- This is the core mechanism that allows processing and capture to continue independently from exact output sync phase, as described in UG934's frame-buffered timing model.

### 7.7 `axi_mem_intercon`

- Functional role: AXI-MM read-path bridge from VDMA MM2S master port to PS7 HP0.
- Main interfaces: `S00_AXI` (from VDMA MM2S), `M00_AXI` (to PS7 `S_AXI_HP0`).
- What it does in this design: adapts/forwards MM2S read bursts to DDR address space.
- Why it exists as a separate block: isolates MM2S traffic path and simplifies arbitration/clock/reset integration.

### 7.8 `axi_mem_intercon_1`

- Functional role: AXI-MM write-path bridge from VDMA S2MM master port to PS7 HP2.
- Main interfaces: `S00_AXI` (from VDMA S2MM), `M00_AXI` (to PS7 `S_AXI_HP2`).
- What it does in this design: forwards S2MM frame writes into DDR address space.
- Why this split is useful: separate HP ports allow concurrent read/write throughput and reduce bidirectional contention.

### 7.9 `v_axi4s_vid_out_0`

- Functional role: AXI4-Stream video to native video interface conversion.
- Main interfaces: `video_in` (AXI4-Stream), `vtiming_in` (from VTC), `vid_io_out` (native video bus), `vid_io_out_clk`, `vid_io_out_reset`, `vtg_ce`, `locked`.
- Configuration highlights: pixels/clock = 1, stream width = 24 bits, async clock support enabled, VTC master/slave mode enabled.
- What it does in this design: repackages AXI4S active-video frames into native video timing domain for TMDS encoding.
- Runtime behavior: reports lock/flow status and gates VTC generation clock-enable (`vtg_ce`) for timing coordination.

### 7.10 `vtg` (`v_tc`)

- Functional role: the timing authority for the output video raster. It defines where each line/frame starts and ends for the output side.
- Configuration highlights: `VIDEO_MODE=720p`, `enable_generation=true`, `enable_detection=false`, `INTERLACE_EN=false`.
- Why this matters: this instance is used as a timing generator only. It is not measuring incoming timing in the current design.

Pin-level explanation:

| Port(s) | Meaning | How used in this BD |
|---|---|---|
| `ctrl`, `s_axi_aclk`, `s_axi_aclken`, `s_axi_aresetn` | AXI4-Lite register interface and its clock/reset | `ctrl` is mapped on AXI-Lite (`0x43C00000`) via `ps7_0_axi_periph`; `s_axi_aclk` on `s_axil_clk_50`; reset from `rst_clk_wiz_0_50M_peripheral_aresetn`; `s_axi_aclken` effectively enabled |
| `clk`, `clken`, `resetn` | Video timing domain clock, enable, and reset | `clk` is in the pixel domain (`PixelClk_Generator_clk_out1`); `resetn` from `rst_vid_clk_dyn_peripheral_aresetn`; `clken` enabled |
| `gen_clken` | Generator clock enable gate | Driven by `v_axi4s_vid_out_0/vtg_ce`, so timing generation is coordinated by AXI4S-to-Video-Out |
| `vtiming_out` | Timing bus bundle (`ACTIVE_VIDEO/HBLANK/HSYNC/VBLANK/VSYNC`) | Connected directly to `v_axi4s_vid_out_0/vtiming_in` |
| `active_video_out`, `hblank_out`, `hsync_out`, `vblank_out`, `vsync_out` | Discrete timing outputs (also represented in `vtiming_out`) | Exposed by the IP; the design primarily consumes the bundled `vtiming_out` interface |
| `irq` | Timing interrupt output | Connected through `xlconcat_0` into PS `IRQ_F2P` |
| `fsync_in`, `fsync_out[0:0]` | Frame-sync handshake signals | `fsync_in` is tied inactive in this build; `fsync_out` is available but not part of the main control loop |
| `sof_state` | Start-of-frame state hint input (optional mode support) | Tied to default inactive value in this build |

Operationally, `vtg` generates periodic output timing and hands that timing to `v_axi4s_vid_out_0`, which then aligns outgoing pixel stream data from VDMA to the generated raster. This is the UG934-compliant split: AXI4-Stream carries active pixels with SOF/EOL markers, while full periodic timing is carried in dedicated timing/control paths.

### 7.11 `video_dynclk`

- Functional role: dynamically programmable MMCM-based clock source for video output path.
- Main interfaces: `s_axi_lite`, `clk_in1` (from PS FCLK), `pxl_clk_5x`, `locked`.
- Configuration highlights: dynamic reconfiguration enabled, input 100 MHz, requested high-speed clock output includes 742.5 MHz setting.
- What it does in this design: provides base clocks used by `DVIClocking_1` to derive synchronized pixel and serial clocks for HDMI.
- Why software control matters: allows runtime mode-dependent clock programming without regenerating the bitstream.

### 7.12 `DVIClocking_1`

- Functional role: local clock-conditioning module for HDMI transmit path.
- Main interfaces: `PixelClk5X` (input), `PixelClk` (output), `SerialClk` (output), `aLockedIn`, `aLockedOut`.
- What it does in this design: takes dynamic-clock outputs and generates stable pixel-domain clocks consumed by `vtg`, `v_axi4s_vid_out_0`, and `rgb2dvi_0`.
- Reset/lock behavior: its lock output is part of pixel-domain reset qualification.

### 7.13 `rgb2dvi_0`

- Functional role: native RGB video to TMDS serializer/encoder for HDMI output.
- Main interfaces: `RGB` (native video in), `TMDS` (to top-level `hdmi_tx`), `PixelClk`, `SerialClk`, `aRst_n`.
- Configuration highlights: active-low reset, external serial clock usage (`kGenerateSerialClk=false`).
- What it does in this design: converts native video timing/data into differential TMDS channels for monitor/display sink.
- Dependency behavior: relies on stable lock from upstream video-out pipeline before deasserting reset.

### 7.14 `clk_wiz_0`

- Functional role: central PL clock generator for control, stream, and camera reference domains.
- Main interfaces: `clk_in1` (from PS FCLK), `clk_out1`, `clk_out2`, `clk_out3`, `locked`.
- Configuration highlights: requested outputs are 50 MHz, 150 MHz, and 200 MHz.
- What it does in this design:
- `clk_out1` drives `s_axil_clk_50` (AXI-Lite/control).
- `clk_out2` drives `mm_clk_150` (stream + VDMA + HP clocks).
- `clk_out3` drives `ref_clk_200` (MIPI D-PHY reference).

### 7.15 `rst_clk_wiz_0_50M`

- Functional role: reset sequencing for AXI/control and stream/memory domains.
- Main interfaces: `ext_reset_in`, `dcm_locked`, `slowest_sync_clk`, `interconnect_aresetn`, `peripheral_aresetn`, `peripheral_reset`.
- What it does in this design: synchronizes reset release against `clk_wiz_0` lock and fans resets to AXI interconnects, VDMA, camera IP AXI-Lite ports, and custom stream IP.
- Practical effect: ensures AXI handshake and register interfaces are quiescent until clocks are stable.

### 7.16 `rst_vid_clk_dyn`

- Functional role: reset sequencing for pixel/native-video timing domain.
- Main interfaces: `ext_reset_in`, `dcm_locked`, `slowest_sync_clk`, `peripheral_aresetn`, `peripheral_reset`.
- What it does in this design: controls reset behavior for `vtg` timing domain and `v_axi4s_vid_out_0` native output side.
- Practical effect: prevents unstable video timing at HDMI output during dynamic clock lock transitions.

### 7.17 `ps7_0_axi_periph`

- Functional role: AXI crossbar/fanout from one PS control master to six AXI-Lite slaves.
- Main interfaces: `S00_AXI` (from PS `M_AXI_GP0`), `M00_AXI..M05_AXI` (to VDMA, dynclk, VTC, DPHY, CSI2 RX, gamma).
- What it does in this design: centralizes control-plane access and maintains consistent address decoding and reset/clocking for all control IP.
- Mapping behavior: all control peripherals are memory-mapped in the PS Data space with 64K windows.

### 7.18 `xlconcat_0`

- Functional role: simple interrupt vector assembly.
- Main interfaces: `In0`, `In1`, `In2`, `dout`.
- What it does in this design: merges `vtg/irq`, `axi_vdma_0/mm2s_introut`, and `axi_vdma_0/s2mm_introut` into PS `IRQ_F2P`.
- Why it matters: gives software visibility into frame/timing events for synchronization and error handling.

## 9. Practical implications for adding new AXI4-Stream video IP

- Insert new processing IP in the stream between `MIPI_CSI_2_RX_0` and `axi_vdma_0/S_AXIS_S2MM` unless a different buffering strategy is required.
- Preserve handshake and framing (`TVALID/TREADY`, `TUSER[0]=SOF`, `TLAST=EOL`) exactly.
- Do not embed timing metadata in stream payload or `TUSER`; use control/timing IP and AXI-Lite.
- If adding configurable IP, attach its AXI-Lite slave to `ps7_0_axi_periph` and assign a non-overlapping base address.
- Keep each new IP in the correct clock/reset domain:
  - stream data path on `mm_clk_150` and `rst_clk_wiz_0_50M_peripheral_aresetn`
  - control path on `s_axil_clk_50`
  - native video output side on pixel clock domain
